# Requirement Analyzer - 使用示例

## 如何使用这个 Skill

当您有一个需求想法时，直接向 Pi 描述您的需求，Pi 会自动激活这个 skill 并按照以下流程分析：

### 使用场景 1: 新功能开发

```
用户: 我想添加一个实时协作编辑功能
```

**Skill 会执行:**

1. **需求捕获** - 询问协作模式、冲突解决策略等
2. **源码分析** - 检查现有状态管理、事件系统
3. **文档研究** - 查询 WebSocket、MCP、同步协议文档
4. **可行性评估** - 评估架构兼容性、技术挑战
5. **制定计划** - 分阶段实施路线图

---

### 使用场景 2: 第三方集成

```
用户: 我想集成 GitHub API 来自动创建 issue
```

**Skill 会执行:**

1. 检查现有的 API 集成模式
2. 查看认证机制
3. 研究 GitHub API 文档和限制
4. 识别扩展点
5. 制定包含错误处理的实施计划

---

### 使用场景 3: 性能优化

```
用户: 系统响应太慢，需要优化
```

**Skill 会执行:**

1. 分析性能瓶颈
2. 检查代码中的低效模式
3. 研究优化技术
4. 评估权衡（内存 vs 速度）
5. 制定渐进式优化步骤

---

## 输出示例

当您提出需求后，会收到类似这样的分析报告：

```markdown
# Requirement Analysis: 实时协作编辑

## 📋 需求摘要
实现多用户实时协作编辑功能，支持同时编辑同一文档

## 🔍 源码分析
- 现有状态管理: 使用 TypeBox schemas
- 事件系统: 支持扩展钩子
- 数据存储: 本地文件系统
- 潜在冲突点: 并发写入、状态同步

## 📚 文档研究
- WebSocket 实现模式
- CRDT (Conflict-free Replicated Data Types)
- Operational Transformation 算法

## ✅ 可行性评估
**复杂度:** 高
**预计工作量:** 40-60 小时

**可行方面:**
- 事件系统支持扩展
- 现有架构可集成 WebSocket

**挑战:**
- 冲突解决需要复杂算法
- 需要引入新的依赖库

## ❓ 需要明确的问题

1. **协作模式**: OT vs CRDT？
   - OT: 成熟但复杂
   - CRDT: 简单但内存开销大

2. **同步粒度**: 字符级 vs 行级？
   - 字符级: 更精细但性能开销大
   - 行级: 性能好但冲突概率高

## 📝 实施计划

### Phase 1: 基础设施 (15 小时)
- [ ] 添加 WebSocket 服务器
- [ ] 设计同步协议
- [ ] 实现基础连接管理

### Phase 2: 核心功能 (25 小时)
- [ ] 实现 CRDT 数据结构
- [ ] 集成到现有编辑器
- [ ] 添加冲突检测

### Phase 3: 优化与测试 (15 小时)
- [ ] 性能优化
- [ ] 边缘情况处理
- [ ] 集成测试

## ⏱️ 预计工作量
总计: 55 小时 (约 7 个工作日)

## 🎯 成功标准
- [ ] 支持 10+ 用户同时编辑
- [ ] 同步延迟 < 100ms
- [ ] 零数据丢失
```

---

## 最佳实践

1. **描述清晰** - 说明要解决的核心问题
2. **提供上下文** - 告知约束条件（时间、技术栈等）
3. **保持互动** - 回答 skill 提出的澄清问题
4. **逐步细化** - 从高层需求开始，逐步深入细节
